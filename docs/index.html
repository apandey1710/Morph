Why a framework?

A program that prints “Hello tests!” and returns zero proves that it runs. It says nothing about whether your reader preserves bytes. A useful test arranges a concrete situation, calls the function, then compares the observed result with an independent expectation.

Manual try/catch blocks can implement a tiny test runner, but that is not the pattern to grow here. Catch2 supplies named cases and diagnostic assertions. GoogleTest and doctest are reasonable alternatives; this notebook chooses Catch2 for its readable expressions and straightforward CMake integration.

The contract comes first

A contract is the behavior a caller can rely on. For these helpers: preserve every byte, truncate overwritten files, accept empty files, and report failed opens. Passing tests provide evidence for those examples; they do not prove all possible IO succeeds.

What you will build

Eight named cases, including independent read and write checks, a shorter overwrite, empty writes, missing paths, and a round trip. You will use real files because the filesystem is the behavior being tested. These are small filesystem integration tests, even if your project groups them under “unit tests.”

The downloadable checkpoint is separate from the engine and needs no graphics library. Its IO code is a teaching snapshot, not a claim that the production writer handles every failure.

Before you begin

You need basic C++ functions and vectors, CMake 3.25 or newer, a C++20 compiler, and a build tool. The first example build downloads pinned Catch2 3.8.1; this is the course version, not a claim about the latest release. Reading the site requires no installation.
