01 / A direction is not yet a camera

One ray answers what lies in one direction. A camera needs a range of directions, and each direction must correspond to a position on a flat screen. We will reuse the lesson 1 DDA helper unchanged; the new work is generating the directions.

Describe the camera with a unit forward vector and a perpendicular plane vector. The plane vector points to the viewer's right and encodes half the camera plane's width at a forward depth of one world unit.

forward = (cos θ, sin θ)
right = (−forward.y, forward.x)
plane = right × tan(FOV / 2)

θ is the camera angle in radians. Our world uses +y downward, so positive θ rotates clockwise. At θ = 0, forward = (1, 0): we look east. Right = (0, 1), which points downward on the overhead map. That is correct: south is on your right when you face east.

Camera basis fragment · requires cmath and raylib.h 

const float angle = 0.0f; // Radians.
const Vector2 forward{std::cos(angle), std::sin(angle)};
const Vector2 right{-forward.y, forward.x};

The dot product of perpendicular vectors is zero: forward.x * right.x + forward.y * right.y = 0. This relationship will make the projection math particularly simple in the next lesson.

02 / Field of view sets the plane width

FOV means field of view: the full angle visible from the camera's left edge to its right edge. Here it is the horizontal field of view. Picture a right triangle with a forward side of length 1 and a sideways side equal to half the camera plane's width.

tan(FOV / 2) = halfWidth / 1
For FOV = 60°: halfWidth = tan(30°) ≈ 0.577

That is why the plane vector has length 0.577 for a 60° view. It is not a unit vector. A larger FOV produces a wider plane and wider-spreading rays. Mathematically, FOV must be greater than 0° and less than 180°; our controls use 30°–110° to avoid extreme projections.

Camera plane fragment · convert degrees to radians before calling tan 

constexpr float pi = 3.14159265358979323846f;
constexpr float fovRadians = 60.0f * pi / 180.0f;
const float halfWidth = std::tan(fovRadians * 0.5f);
const Vector2 plane{-forward.y * halfWidth,
                     forward.x * halfWidth};
The purple line is a construction

The lab draws the camera plane centered at player + forward. It is not a physical wall and does not block a ray. It represents a flat screen at depth 1, making ray generation easy to see.

03 / Sample a screen, not a circle

Let u describe a horizontal position across the camera plane. The left edge is −1, the center is 0, and the right edge is +1. Then a ray through that point has direction:

rayDirection = forward + u × plane

Notice that the player's position is absent from this expression. It is a direction vector, not a world-space endpoint. The ray origin is still the player.

u Direction at 60° FOV, facing east Meaning
−1 (1, −0.577) Left edge, pointing northeast
0 (1, 0) Straight ahead
+1 (1, +0.577) Right edge, pointing southeast

For N rays, sample the centers of N equal-width intervals across the plane. For ray index i from 0 to N − 1:

u = 2 × (i + 0.5) / N − 1

The +0.5 moves from the left edge of each interval to its center. With N = 5, the samples are −0.8, −0.4, 0, 0.4, and 0.8. The extreme rays lie slightly inside the field of view edges, just as the centers of the first and last screen pixels lie inside the screen boundary.

Do not normalize these rays

Their forward component is deliberately 1. The center ray has length 1; edge rays are longer. The DDA helper accepts both. Keeping this construction intact means the returned t is already forward camera depth. Normalization is possible, but then you must convert ray length back to depth before projection.

Why not divide the angle evenly?

Equal angle increments are fine for a radial sensor display, but they do not correspond to equal spacing on a flat image plane. Sideways position on the plane is proportional to tan(angle), not angle. If you assign equally spaced angles directly to equally spaced screen columns, the horizontal projection is wrong. Sampling u uniformly gives the geometry of a flat camera.

04 / Draw a modest number of rays

Use 31 rays for the overhead debug view: enough to see the fan, few enough to inspect individual hits. The full renderer will later use one per screen column. The following fragment depends on castRay and toScreen from lesson 1, plus the forward and plane vectors above. Run it after drawing the map and before drawing the player.

Drawing-loop fragment · rayCount must be positive 

constexpr int rayCount = 31;
for (int i = 0; i < rayCount; ++i)
{
    const float u = 2.0f * (static_cast<float>(i) + 0.5f) / rayCount - 1.0f;
    const Vector2 rayDirection{
        forward.x + u * plane.x,
        forward.y + u * plane.y
    };
    const auto hit = castRay(level, playerPosition, rayDirection);
    if (!hit)
    {
        continue; // Open map boundary or invalid origin: nothing to draw.
    }
    const Color color = hit->side == Side::X ? SKYBLUE : ORANGE;
    DrawLineV(toScreen(playerPosition), toScreen(hit->position), color);
    DrawCircleV(toScreen(hit->position), 3.0f, color);
}
DrawCircleV(toScreen(playerPosition), 5.0f, WHITE);

Rotation changes the camera basis, not the map. Keep a mutable angle outside the main loop, update it from keyboard input using frame time, then recompute both forward and plane together each frame.

Rotation fragments · do not also keep the earlier constant angle declaration 

// Before the main loop:
float angle = 0.0f;

// Inside the loop, before generating forward and plane:
const float turnSpeed = 1.2f; // Radians per second.
if (IsKeyDown(KEY_LEFT))
{
    angle -= turnSpeed * GetFrameTime();
}
if (IsKeyDown(KEY_RIGHT))
{
    angle += turnSpeed * GetFrameTime();
}

The checkpoint includes this rotation, but intentionally keeps the player position fixed. Movement and collision deserve a separate lesson: seeing a wall does not prevent walking through it.

05 / Inspect the camera before projection

  1. Face east at 60° FOV. The upper rays should point northeast and the lower rays southeast. If this is reversed, the plane vector has the wrong sign.
  2. Reduce the FOV. The fan should narrow while the center ray stays fixed.
  3. Change the ray count from 3 to 81. The world and FOV should stay fixed; you are changing only sampling density.
  4. Rotate through 90°. The fan should rotate rigidly. A stale plane vector causes skewing.
  5. For every hit, check that dot(hit.position − playerPosition, forward) approximately equals hit.t. Expect small floating-point differences.
Checkpoint

You are ready to project when each sample has a stable left-to-right position, every ray hits the correct first wall, and forward depth agrees with the DDA parameter.
