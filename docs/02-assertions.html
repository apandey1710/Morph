MORPH / LESSON 02

A passing test
should mean something.

Replace manual exception bookkeeping with clear expectations. Learn when to stop, when to continue, and how to make a failure useful.

Real project examplesRunnable C++ checkpointNo custom test runner

Arrange → act → assert

Arrange the starting state. Act by calling the behavior under test. Assert something a caller cares about. A name such as “writeFile truncates a longer file” states the promise; “test 4” does not. 

// Fragment: directory is a TempDirectory from lesson 3.
const auto path = directory.file("missing.bin");      // Arrange
REQUIRE_FALSE(std::filesystem::exists(path));
REQUIRE_THROWS_AS(morph::io::readFile(path),           // Act + assert
                  std::runtime_error);

No local try/catch is needed. An exception is the expected result of this API call, so the assertion names its type. Avoid requiring exact error wording unless the wording itself is part of the API contract.

Stop only when continuing is unsafe

AssertionUse it for
REQUIRE(expression)A prerequisite: stop this case if it fails.
CHECK(expression)An independent observation: report failure and continue.
REQUIRE_THROWS_AS(call, Type)A documented exception type.
REQUIRE_NOTHROW(call)A meaningful promise that the call succeeds. 
// Fragment: actual is a byte vector returned by the reader.
REQUIRE(actual.size() == 6);  // Guards the indexing below.
CHECK(actual[0] == std::byte{0x00});
CHECK(actual[5] == std::byte{0xFF});

Using CHECK for the size would permit invalid indexing after a failed prerequisite. But for complete byte preservation, prefer REQUIRE(actual == expected): it checks length and every element without indexing.

Unexpected exceptions are reported by the framework. Wrapping every case in a catch-all can hide failures, especially if the catch prints a message and returns normally. Plain assert is also a poor default for a suite because builds with NDEBUG can remove it.

A green result can be weak evidence

Select the corrupted payload and check only its size. The test passes because corruption did not change the length. Switch to exact equality to detect it. “File exists” and “file is nonempty” are useful prerequisites, but neither proves correctness.

Independent cases, shared setup 

// Fragment from the full IO test file; seed and TempDirectory are helpers.
TEST_CASE("writeFile creates and truncates empty files", "[io][write]")
{
    TempDirectory directory;
    const auto path = directory.file("empty.bin");
    SECTION("new file") {}
    SECTION("existing file") { seed(path, payload()); }

    std::vector<std::byte> empty;
    morph::io::writeFile(path, empty);
    REQUIRE(std::filesystem::exists(path));
    CHECK(std::filesystem::file_size(path) == 0);
}

For these two sibling SECTIONs, Catch2 reruns the test case for each path. The setup is recreated; the second section does not inherit a file from the first. Both paths share the assertions after the sections. CTest discovery lists the TEST_CASE once, not each section separately.

Use separate cases for distinct promises. Use sections sparingly when two starting states genuinely share the same action and expectation. Tags such as [read] and [write] help filter within the executable.

Read a failure as evidence 

// Illustrative diagnostic, not captured output:
writeFile truncates a longer file
io_tests.cpp:123: FAILED:
  CHECK( std::filesystem::file_size(path) == 1 )
with expansion:
  6 == 1

The observed file has six bytes after a one-byte write. That points toward retained trailing data. It does not justify changing the expectation to six: the expected size comes from the overwrite contract, not the implementation’s current behavior.

Try it

In a disposable copy of the checkpoint, change the writer to open with std::ios::binary | std::ios::app. Build and run. The new-file test may still pass; the shorter-overwrite test should fail. Restore the writer afterward. Deliberately introducing a bug to assess your tests is called mutation testing.
