01 / Depth is how far forward, not how far along

Stand in front of a flat wall. The point straight ahead is closer in straight-line distance than points off to either side. Yet all those points share the same forward depth, and the wall's top edge should look straight when it is parallel to the screen.

If you shrink wall strips using the longer edge-ray distances, the edges become too short. The result is the familiar fisheye distortion: a flat wall appears to bow. The cure is to project using the component of the hit displacement along the camera's forward direction.

H = hitPosition − playerPosition
rayLength = length(H)
cameraDepth = dot(H, forward)

The dot product is H.x * forward.x + H.y * forward.y. Because forward has unit length, it measures how much of H points forward. Equivalently, for a unit ray direction making angle α with forward, cameraDepth = rayLength × cos(α).

Why our DDA parameter already is depth

We generated the ray as D = forward + u × plane and did not normalize it. We also know that the hit displacement is H = tD. Substitute those two facts:

depth = dot(tD, forward)
      = t × [dot(forward, forward) + u × dot(plane, forward)]
      = t × [1 + u × 0]
      = t

This is a consequence of the camera construction, not a universal property of DDA. If you normalize D, then t becomes traveled ray length and you must calculate depth separately. Do not apply another cosine correction to our already-correct t.

A numerical check

For a front-facing wall at depth 4 and a 60° FOV, the edge ray is D ≈ (1, 0.577). It reaches the wall at t = 4, but travels 4 × √(1 + 0.577²) ≈ 4.619 world units. Dividing by 4.619 instead of 4 makes that edge strip about 13.4% too short.

02 / Similar triangles turn units into pixels

A wall's projected height gets smaller in inverse proportion to its depth: double the depth, halve its pixel height. To determine the actual number of pixels, we need the camera's focal distance measured in pixels.

Let W and H be the viewport width and height in pixels. Let h be wall height in world units and z be positive camera depth in world units. With horizontal FOV and square pixels:

focalPixels = (W / 2) / tan(FOV / 2)
stripHeight = h × focalPixels / z

The first expression is the same camera-plane triangle from lesson 2, now measured on the screen. The second comes from similar triangles: the ratio of projected height to focal distance equals wall height divided by world depth. World units cancel, leaving pixels.

At W = 960 and FOV = 60°, focalPixels ≈ 831.38. A wall of height 1 at depth 4 occupies about 207.85 pixels. At depth 8 it occupies about 103.92 pixels.

Why not just use screenHeight / depth?

That common shortcut silently chooses a particular focal distance. Using the horizontal FOV explicitly keeps the image consistent when the window aspect ratio or FOV changes. The vertical FOV follows from 2 × atan((H / 2) / focalPixels).

For this lesson, the eye is at half the wall height and the camera has no pitch or roll. The horizon is halfway down the viewport, so center every strip vertically:

top = H / 2 − stripHeight / 2
bottom = H / 2 + stripHeight / 2

These centered formulas rely on that eye-height assumption. Variable wall heights, stairs, or an eye above the midpoint need separate top and bottom projections.

03 / One ray for each screen column

Keep the same sampling formula, but replace the debug ray count with the viewport width. Each x coordinate owns a one-pixel-wide wall strip. Cast a ray, obtain its depth, calculate the strip's height, and shade it by which side was crossed.

The following is the projection core from the complete checkpoint. It runs inside the drawing loop after the camera basis is computed. It requires the shared headers from the earlier lessons and <algorithm> for clamping.

Projection fragments · shared helper cameraRay returns forward + u × plane 

// Once before the loop; this example uses a fixed 960 × 540 viewport.
const double focalPixels = (screenWidth * 0.5) / std::tan(fovRadians * 0.5);
constexpr double wallHeight = 1.0;
constexpr double nearDepth = 0.001; // One thousandth of a world cell.

// Inside BeginDrawing / EndDrawing:
ClearBackground(Color{22, 31, 42, 255});
DrawRectangle(0, screenHeight / 2, screenWidth, screenHeight / 2,
              Color{34, 41, 43, 255});

for (int x = 0; x < screenWidth; ++x)
{
    const float u = 2.0f * (static_cast<float>(x) + 0.5f) / screenWidth - 1.0f;
    const Vector2 ray = cameraRay(forward, plane, u); // Not normalized.
    const auto hit = castRay(level, playerPosition, ray);
    if (!hit)
    {
        continue;
    }

    const double depth = std::max(hit->t, nearDepth);
    const double height = wallHeight * focalPixels / depth;
    const double top = std::clamp((screenHeight - height) * 0.5, 0.0,
                                  static_cast<double>(screenHeight));
    const double bottom = std::clamp((screenHeight + height) * 0.5, 0.0,
                                     static_cast<double>(screenHeight));
    const int yStart = static_cast<int>(std::floor(top));
    const int yEnd = static_cast<int>(std::ceil(bottom));
    const Color shade = hit->side == Side::X
        ? Color{111, 207, 192, 255}
        : Color{58, 130, 136, 255};
    DrawRectangle(x, yStart, 1, yEnd - yStart, shade);
}

The two wall colors are simple orientation cues, not a lighting model. They help you see corners. The floor and ceiling are flat background colors, not floor or ceiling raycasting. All the wall-intersection and projection math runs on the CPU; raylib presents the rectangles. A CPU framebuffer can replace the draw calls later without changing the geometry.

04 / Handle the edges deliberately

  • Zero or tiny depth: a player on a wall boundary can produce t = 0. The 0.001-world-unit lower bound prevents division by zero and caps the projected height. It is a numerical guard, not a collision radius or a physical near-plane clipping system.
  • Large projected heights: clamp the floating-point top and bottom to the viewport before converting them to integers. This avoids overflowing integer coordinates for nearby walls.
  • Pixel coverage: floor the top and ceil the bottom so a visible fractional strip does not disappear. The rectangle covers the interval [yStart, yEnd).
  • No hit: leave the existing sky/floor background in that column. The DDA helper does not invent a wall at an open map edge.
  • Resize or change FOV: recalculate focalPixels from the actual viewport dimensions and current FOV. The downloadable checkpoint uses a fixed-size window and fixed 60° FOV.
  • Movement: the player stays fixed here. If you add movement, use a separate collision query that accounts for the player's size, especially at corners.

05 / Prove the projection works

  1. In the browser lab, choose the flat-wall preset. It places the player at (4.5, 4.5), facing south at 90° with a 60° FOV. The south wall has depth 2.5 across the entire view, so every strip should have equal height.
  2. Toggle ray length while using that preset: the top and bottom edges should bow. Turn the toggle off: they should straighten. Reset camera returns to the original spawn at (2.5, 1.5), facing east.
  3. Keep direction fixed and widen the FOV. More of the room should become visible and the center wall strip should get shorter, because focalPixels decreases.
  4. For a controlled numeric experiment, compare a wall at depth 4 to one at depth 8. The projected height should halve, aside from integer rounding.
  5. In the C++ checkpoint, press F. For the same controlled flat-wall experiment, set playerPosition to (4.5f, 4.5f) in scene.hpp and the initial angle to pi / 2 in the lesson source. The intentionally wrong branch multiplies t by the ray's length. Restore camera depth before continuing the renderer.
